## Problem Statement

SeptMuse 已完成 850 测试基线（截至 2026-07-27 实测：850 passed, 36 skipped；P0-Task 1/4, P1-Task 1/2, P2-Task 1, P3-Task 1），覆盖 CRUD+search+entity+reranker+bitemporal+LLM provider。但**零个外部 agent 消费它**。28 Task 路线图（P0-P6）剩余 21 Task 全是记忆内部特性扩展，零个 Task 验证外部消费。平台 agent 运行时未就绪，没有具体消费方。

诊断揭示三层一致信号：
- Q1 需求：规划中未落地——无消费方
- Q2 现状：无记忆从零开始——因为没有 agent
- Q3 具体人：运行时也未就绪——连 runtime 都没有

这是 "Infrastructure in Search of Application" 失败模式：在消费层不存在时预先建基础设施。

## Demand Evidence

预期需求（平台规划了"带记忆 agent"角色），但无实际消费方。Q1-Q3 诊断揭示消费层 agent 和 runtime 都不存在。

这是预期需求，不是行为证据。但用户在 P1 前提上推回（"先地基后上层"，有理由），表明这是有 conviction 的平台策略判断，不是盲目建基础设施。内部平台场景下，预期需求可成立，前提是尽快用一个集成示例将其转化为行为证据。

## Status Quo

上层 agent 无记忆，从零开始——因为 agent 还不存在。没有临时方案凑合，没有外部库替代，是纯粹的"缺失"。

这看似是"问题不够痛"的信号，但对 agent 应用，"无记忆"确实是真痛点（用户讨厌每次重新介绍自己）。痛点载体（agent）还没出现是平台阶段问题，不是记忆系统价值问题。

## Target User & Narrowest Wedge

- **Target**：平台 agent 开发者（内部）——未来第一个建消费 agent 的人
- **Wedge**：CLI chatbot 示例 agent（Approach A），通过 **Memory facade 直连**（不是 MCP）消费 SeptMuse

**为何 facade 而非 MCP**：MCP stdio transport 占用 stdin/stdout 做 JSON-RPC，CLI chatbot 也要 stdin/stdout 与用户交互——同进程两个 stdio 主人，架构冲突不可解决。MCP SSE/HTTP 需先起 server，不再是"单文件"。facade 是内部消费 agent 的自然路径（`from septmuse import Memory`），`examples/quickstart.py` 已隐式验证可 import，但未验证完整对话闭环。MCP 验证留给独立 smoke test。

楔子目标不是"建一个产品"，而是**验证可消费性 + 反推真实需求**：
1. 证明 SeptMuse 当前 850 测试基线可被 agent 通过 facade 端到端消费
2. 记录哪些 facade 方法调用顺畅、哪些别扭、哪些缺失
3. 用这些观察重排 21 Task 优先级——把"消费方真正需要的"排前面

## Constraints

- PYTHONPATH=src 运行（包未 pip install -e .）
- ruff format 在 Windows 上会清空文件——用 `ruff format --check`
- 中文输出强制（AGENTS.md）

- 对话回复层不用 MockLLM（MockLLM 只返回 `{"facts":[...]}` JSON，不能生成人话）——用规则模板拼接记忆事实，或 `--llm` 切换真实 LLM 生成回复

## Premises

用户已 agree/disagree 以下前提：

1. **建设顺序**：DISAGREE（用户推回）—"先地基后上层"。用户认为记忆系统是地基，应先建好再起 agent，否则 agent 建到一半发现记忆缺口更糟。这是有理由的推回，记录为创始信号。
2. **路线图来源**：AGREE — 28 Task 从 6 个已落地系统抄来，需按真实消费场景重新验证优先级。
3. **地基充足性**：AGREE — 850 测试基线已是"足够的地基"，剩余 21 Task 都是特性扩展，不是地基。
4. **正确楔子**：AGREE — 楔子是集成示例 agent，不是更多记忆特性（cognify/dream/conflict）。

**修正理解**：foundation-first 哲学成立，但 foundation 内部的特性优先级由消费场景驱动。850 测试基线 = 完成地基。下一步不是 28 Task 路线图上的任何 Task——是路线图外的集成示例 agent。

## Approaches Considered

### Approach A: CLI Chatbot 示例（最小）—— 已选定

`examples/cli_chatbot.py` 单文件 Python CLI 聊天机器人。通过 **Memory facade 直连**（`from septmuse import Memory`），展示 add/search/get/update 在真实对话中的流转。对话回复用规则模板拼接记忆事实（默认），或 `--llm` 切换真实 LLM 生成回复。文档化 facade 集成模式。

- **Effort**: S（~1 文件，4-6 小时——比原估"几小时"更现实，含对话逻辑 + 结构化反馈 + 多轮记忆注入）
- **Risk**: Low
- **Pros**: 最快到反馈；低摩擦验证 facade 可消费；结果决定 B/C 是否需要；无 stdio 架构冲突
- **Cons**: 单文件不能展示 SeptMuse 全部能力；不验证 MCP 跨进程路径（留给独立 smoke test）
- **Reuses**: Memory facade（`orchestration/memory.py`）、MockLLM（仅记忆抽取层）、HashEmbedder（零配置）
- **为何先验 facade 而非 MCP**：MCP stdio 与 CLI chatbot stdin/stdout 冲突不可解决；facade 是内部消费 agent 的自然路径；`examples/quickstart.py` 已验证可 import 但未验证对话闭环

### Approach B: 参考 Agent 应用（理想）

`examples/reference_agent/` 多文件参考应用。展示 facade+REST 集成+context window 管理+记忆生命周期+双时态查询+实体感知检索。包含集成测试验证 agent 端到端可消费 SeptMuse。

- **Effort**: M（~5-8 文件，1-2 天）
- **Risk**: Med
- **Pros**: 多维度展示 SeptMuse 能力；可复用为平台 agent 起点；集成测试验证端到端
- **Cons**: 在 A 验证可消费性前可能过早投入；可能建了不需要的维度展示
- **Reuses**: Memory facade、REST API、bitemporal、entity、reranker

### Approach C: Agent SDK + 示例（横向）

先建薄 SDK 层（`septmuse.agent_sdk`），包装 facade/REST 为 agent 友好原语：`agent.remember/recall/context_for`。配最小示例 agent 使用该 SDK。这是 letta/mem0 的模式——提供 agent 友好 API 而非裸记忆 API。

- **Effort**: L（~2-3 天）
- **Risk**: Med-High
- **Pros**: 建立 agent 友好 API 作为一等表面；对齐 letta/mem0 模式
- **Cons**: 在 A 揭示裸 facade API 是否够友好前就重构，可能过度工程
- **Reuses**: Memory facade、REST API

## Recommended Approach

**Approach A: CLI Chatbot 示例（最小）**

理由：用户目标是"验证可消费 + 反推需求"。A 最快到反馈。其结果决定 B/C 是否需要——B 是 A 验证通过后的自然演进；C 是当 A 揭示裸 MCP API 不够友好时才需要的重构。先 A，再根据反馈决定 B/C。

## Open Questions

1. **对话回复层 LLM 选型**：MockLLM 只能做记忆抽取（返回 `{"facts":[...]}` JSON），不能生成对话回复。默认 verbatim 模式（`infer=False`，不调任何 LLM，每条消息原文存入），对话回复用规则模板拼接记忆事实（零依赖，确定性）。`--llm` 参数切换真实 LLM：此时 `infer=True` 走 LLM 抽取 + LLM 生成回复。`--llm` 映射到 `SEPTMUSE_LLM` 环境变量（openai/ollama/anthropic/dashscope）。`--llm mock` = 显式注入 `llm=MockLLM()` + `infer=True` 做 fact 抽取（但回复仍用规则模板）。
2. **运行命令**：对齐 `examples/quickstart.py` 的直接脚本模式——`PYTHONPATH=src python examples/cli_chatbot.py`（不是 `-m examples.cli_chatbot`，因为 `examples/` 无 `__init__.py`）。
3. **user_id 透传**：facade 直连模式不走 MCP contextvars。`Memory.__init__` 不接受 `user_id` 参数——`user_id` 是 per-method-call 的 kwarg。chatbot 自存 `user_id` 实例变量，每次调 `memory.add(user_id=...)` / `memory.search(user_id=...)` / `memory.update(user_id=...)` 时作为 kwarg 传入。`memory.get(memory_id)` 不接受 `user_id`（单用户示例可接受）。默认 `user_id="default"`，`--user` 参数覆盖。
4. **边界情况**：
   - 空记忆时 search 返回空列表 → chatbot 提示"我还没有关于你的记忆"
   - LLM 未配置时降级为规则模板模式 + 警告
   - 多轮对话 context window 溢出 → 只注入 top-3 相关记忆（按 score 排序）
5. **结构化反馈格式**：chatbot 退出时输出 JSON 到 stdout：
   ```json
   {
     "tools_used": [{"method": "add", "count": 5, "experience": "smooth"},
                     {"method": "search", "count": 12, "experience": "awkward"}],
     "missing_capabilities": ["想批量删除但 facade 无 delete_by_query"],
     "recommendation": "21 Task 中应优先 P3-Task 2（LLM 抽取）因为..."
   }
   ```
6. **MCP 验证独立 track**：A 验证 facade 后，另起 `examples/mcp_smoke_test.py` 验证 MCP SSE/HTTP transport 可消费（需先起 server），不阻塞 A。

## The Assignment

**具体行动**（不是"去建它"）：

1. 建 `examples/cli_chatbot.py`，默认 verbatim 模式（`infer=False`，每条用户消息原文存入，不调任何 LLM，对话回复用规则模板拼接记忆事实），`--llm` 参数切换真实 LLM（`infer=True` 走 LLM 抽取 + LLM 生成回复）
2. 实现 4 个操作的闭环：用户输入 → chatbot 调 `memory.add(user_id=...)` 存记忆（默认 verbatim 存原文）→ 下次输入时 chatbot 调 `memory.search(user_id=...)` 注入相关记忆到 context → 规则模板拼接回复（支持 `memory.get(memory_id)` 查特定记忆、`memory.update(user_id=...)` 修正）
3. 运行它，记录三个观察：
   - **顺畅**：哪些 facade 方法调用体验好？（说明 API 设计对的）
   - **别扭**：哪些 facade 方法调用体验差？（说明 API 需要改进——这是 21 Task 重排的输入）
   - **缺失**：chatbot 想做但 facade 没提供的能力？（说明 28 Task 路线图漏了什么）
4. 用这三个观察重排 21 Task 优先级——把"消费方真正需要的"排前面，把"特性补齐但消费方不需要的"排后面
5. 在 `docs/plans/development-roadmap.md` **新建**"优先级重排"章节（当前不存在），记录重排结果和依据

**完成标志**：chatbot 能跑 + 三类观察记录完 + 21 Task 优先级重排完成 + 重排章节写入 development-roadmap.md。
