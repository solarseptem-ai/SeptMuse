# SeptMuse 记忆架构分析与开源对比

> **日期**: 2026-07-29
> **状态**: Analysis
> **范围**: 对比 6 家开源实现，诊断 SeptMuse 三维正交架构图的问题，提出修复方向

---

## 一、6 家开源架构图风格对比

| 项目 | 图风格 | 画的是什么 | 三维矩阵 | 组合矩阵 | 数据流图 |
|------|--------|-----------|:-------:|:-------:|:-------:|
| **mem0** | 纵向管道图 | 写入3步 / 检索3步 | 否 | 否 | 是 |
| **ReMe** | 水平调用链 + 分层表 | 入口→执行路径 + 能力边界 | 否 | 否 | 是(mermaid) |
| **MemOS** | 纵向分层 + 抽象链 | 执行路径 + L1/L2/L3演化 | 否 | 否 | 部分 |
| **cognee** | 双流概念图(图片) | remember + recall 两流 | 否 | 否 | 是 |
| **graphiti** | 组件表 + GIF | 概念定义(temporal核心) | 否 | 否 | 否 |
| **letta** | (已迁移，无图) | — | 否 | 否 | 否 |
| **SeptMuse** | **三维正交 + 组合矩阵** | **内容类型×存储形态×横切关注点** | **是** | **是** | **否** |

### 核心发现

1. **SeptMuse 是唯一用三维正交矩阵的**——其余 5 家全部用数据流管道图或调用链图
2. **mem0 的管道图最实用**——用户看完就知道 `add()` 和 `search()` 内部发生了什么
3. **ReMe 开篇声明能力边界**——SeptMuse 什么都往矩阵里塞，反而造成层级混乱
4. **MemOS 有 L1/L2/L3 抽象链**（事实→经验→认知→技能），是演化链而非正交分类
5. **没有一家画组合矩阵**——SeptMuse 的 4×6 矩阵是独创设计，空白问题也是独创的

## 二、SeptMuse 三维正交架构图问题诊断

### 2.1 身份记忆混轴（严重度：高）

**现象**: 架构原则声明"禁止混轴"，但身份记忆横跨工作记忆和语义记忆——组合矩阵 `语义×block=(✅)` 注释说"身份子类借用 block"。

**开源对比**: 没有一家把身份当独立类型——mem0 存为 fact+tag，letta 存为 persona block，graphiti 存为 entity。

**根因**: 身份是**跨类型双形态存在**（persona block 在 context window + 语义事实在长时存储），强行归入单一类型违反正交原则。

**修复方向**: 明确身份是"双形态同步"而非单类型子类，在矩阵中标注 `[sync]` 而非归入单一格子。

### 2.2 激活记忆与 Block 概念混搭（严重度：中）

**现象**: 激活记忆(KV-Cache)放在工作记忆下，但两者操作语义完全不同（文本 vs 张量，context window vs GPU 显存，自编辑 vs 前向计算注入）。

**开源对比**: MemOS 是唯一有 KVCache 的，它把 activation 作为独立 memory type（和 textual/parametric 平行），不放在 working memory 下。

**根因**: 按生命周期分类（都"不跨会话"）而非认知功能分类，与平面 A "内容类型"定义不一致。

**修复方向**: 激活记忆从平面 A（内容类型）移到平面 B（存储形态），工作记忆只用 block。

### 2.3 感觉记忆不参与三维组合（严重度：低）

**现象**: 感觉记忆列在平面 A，但"<1s, 不持久化"，不参与任何存储形态，也不需要横切管理。

**开源对比**: 没有一家提"感觉记忆"。

**根因**: 强行对齐 Atkinson-Shiffrin 认知科学模型，但其他项目不追求这个——图越学术化越容易自相矛盾。

**修复方向**: 从平面 A 移除，在架构总览中标注为"瞬时态，不参与 B/C 平面"。

### 2.4 组合矩阵空白缺论证（严重度：中）

**现象**: 24 格只有 8 格成立，没说明为什么"不成立"。部分空白是"当前不做"而非"概念不成立"。

**开源对比**: 没有一家画矩阵，所以不存在这个问题。

**根因**: 矩阵是独创设计，独创的空白需要独创的论证。

**修复方向**: 每个空白格标注 `N`（概念不成立）vs `—`（当前不实现）。

### 2.5 源同步器概念层级不对等（严重度：低）

**现象**: 平面 C 列了 6 个横切关注点，但"源同步器"是平面 B 内部的多形态一致性机制。

**开源对比**: ReMe 用"能力边界"声明排除不归自己管的东西。

**修复方向**: 源同步器从平面 C 移到平面 B 内部。

### 2.6 缺数据流向图（严重度：高）

**现象**: 只有结构图（有哪些组件），没有行为图（数据如何流动）。

**开源对比**: **mem0 的管道图最实用**——写入3步/检索3步一目了然。**这是 SeptMuse 最大的缺失**。

**修复方向**: 补 capture→persist→retrieve 的管道图。

### 2.7 实现层与设计层映射不清（严重度：中）

**现象**: 设计图是三维正交，实现图是传统分层，两者映射靠代码目录推断。

**开源对比**: MemOS 的架构图直接对应目录结构。

**修复方向**: 在架构图中标注目录映射（`content_types/` = 平面A 等）。

## 三、修复方向总结

| 问题 | 修复 | 影响范围 |
|------|------|----------|
| 身份混轴 | 双形态标注 `[sync]` | 矩阵 + 平面A §3.3 |
| 激活与Block混搭 | 激活移到平面B | 矩阵 + 平面A §3.1 |
| 感觉记忆 | 从平面A移除 | 矩阵 + 平面A |
| 矩阵空白 | 标注 N vs — | 组合矩阵 |
| 源同步器 | 移到平面B | 平面B §4 + 平面C §5 |
| 缺数据流图 | 补写入/检索管道 | 新增 §6 §7 |
| 映射不清 | 标注目录映射 | 架构总览 §2 |

**核心结论**: SeptMuse 的三维正交矩阵是学术创新，但需要补数据流管道图（mem0 风格）让用户看懂"怎么用"。详细完整设计文档见 `2026-07-29-memory-system-design.md`。
